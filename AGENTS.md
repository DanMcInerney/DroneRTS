# DroneRTS development

This is a standalone Git repository for a local Three.js drone swarm RTS. Two teams of three drones gather finite salvage, share income, buy gun/armor/miner attachments and fight until one team survives. The geographic world is Cincinnati with a detailed downtown battlefield and a schematic wider municipal landscape. Read [README.md](README.md) for setup, [ARCHITECTURE.md](ARCHITECTURE.md) for ownership, and [CITY.md](CITY.md), [NETWORK.md](NETWORK.md), and [MAVLINK.md](MAVLINK.md) for their components.

## Run and verify

- Install JavaScript dependencies with `npm ci` and Python helpers with `npm run network:setup`. Node 22+ is required; Python 3.12.4 is the tested interpreter. Python dependencies belong in `.venv`.
- `npm run dev` serves the game at `http://127.0.0.1:4317`. `npm run build` checks TypeScript and creates the production bundle; `npm start` serves that bundle.
- `npm test` runs the automated suite, including real Zenoh and MAVLink helper integration tests, without model inference. Run relevant tests and the build after implementation changes.
- Live gameplay also requires an installed, signed-in Codex CLI and an open browser to provide camera images. Launch match starts both teams with the same elimination/resource objective; Send transmits additional instructions to blue only. The enemy team acts independently.
- All gameplay actors and live playtest agents must use **gpt-5.6-luna / xhigh**, per the user's cost preference. Do not silently substitute another model or reasoning effort. This preference is scoped to gameplay/playtesting.
- Before restarting a server or launching a test mission, inspect `/api/state`. Preserve an active player session on port 4317; prefer an isolated server on 4318 for automated live trials. If another checkout owns 4318, `playtest-focused.ts` accepts `RTS_TRIAL_PORT` for another free port and still refuses player port 4317 or an occupied trial port. Keep live trials bounded and stop the test fleet/server afterward.
- Use the Codex sidebar browser for watchable playtests when available. The user has also authorized isolated Playwright as a fallback. Do not start inference merely to validate documentation or a folder move.
- `node --import tsx scripts/verify-rts.ts` exercises a deterministic browser fixture without inference. `node --import tsx scripts/playtest-rts.ts` runs bounded real two-team Luna/xhigh inference. Current results belong in `RTS-PLAYTEST.md`; preserve historical reports as evidence of their own revisions.
- Focused evaluation commands and their fixture boundaries are documented in README.md. `scripts/measure-controls.ts` needs no server or inference. `scripts/playtest-focused.ts` owns port 4318 and launches actual actors; do not run it alongside another server on that port. Analyze saved evidence with `scripts/analyze-trial.ts` before claiming a moving-target hit or autonomous skill.

## Preserve the experiment

- Each of the two parent sessions mechanically forwards its team's original instructions to exactly three clean-context native drone subagents. Parents do not plan, assign search areas, choose loadouts or solve the mission.
- Each drone learns through its own camera, local XYZ position, heading and timestamp, plus received peer/player messages. The user-authorized opening commander briefing supplies common recognition and interaction knowledge: resource/charging cube appearance and use, and friendly/enemy drone colors and shape. Keep that briefing in `shared/mission.ts`; it supplies no battlefield locations or calibration. Position is simulator-local XYZ, not latitude/longitude. There is no roll/pitch sensor.
- Automatic opening missions, drone bootstrap instructions and tool descriptions explain the objective, rules and interface. The user also authorizes explaining private peer radio and asking teammates to share relevant observations, intentions and help requests, coordinate shared spending and pursue the objective efficiently together. Before opening purchases or departure, instruct drones to agree through actual peer replies on an initial plan, first item and purchaser. Do not prescribe tactics, roles, equipment choices, exploration routines, routes, positioning, fixed radio formats or reporting schedules. Let the drones develop those themselves. Explicit player-written instructions still relay unchanged.
- Keep map geometry, resource locations, enemy telemetry, combat constants, movement scale/speed, axis conventions, camera field of view and future observations out of drone prompts and tool responses. These facts may exist in developer documentation and renderer/simulator code; gameplay agents run in an isolated directory without access to them. Drones begin with no scene calibration and learn through controlled observations and actual peer messages.
- Preserve fresh sensor/inbox bundles at drone tool boundaries, asynchronous movement and waits, durable peer mail, and per-drone mission versions. A model's private reasoning cannot be interrupted to inject input.
- Peer traffic uses two isolated native Zenoh networks, each containing only its own three-drone roster and operator bridge. The vehicle adapter uses MAVLink 2 packets with six distinct vehicle IDs. Keep failures explicit; do not introduce a silent in-memory fallback for live gameplay. Loopback peer connections simulate partitions but are not a physical RF mesh or a full autopilot.
- Player-visible scores, map markers, inventories and world state are not agent observations. Per the user's cube simplification, entering a translucent yellow resource cube automatically mines; entering a friendly team-colored cube automatically charges. Drone-center occupancy of the visible volume is authoritative, with no camera-evidence gate or extra reach/visibility requirement. Never expose resource/pad locators or arbitrary target IDs. Cube colors and automatic interactions may be explained in tool descriptions; locations, dimensions and calibration remain private. Each team starts with 30 shared salvage and buying available. Gun equipment unlocks firing/rearming; optics unlock camera mode. Own equipment, ammunition, camera mode, mining/charging state, service status and shared balance are allowed feedback. Shots follow actual aim and collide physically, without enemy-ID targeting or hidden hit receipts.
- Preserve two module slots, atomic purchases/replacements and finite ammunition. Fitting equipment and timed rearming require occupancy of a friendly service cube. Rearming remains cancellable and refunds its reservation exactly once. Charging is continuous, free and automatic while inside, even when moving; leaving retains charge already gained. Base capacity is 300, the battery pack doubles it to 600, and refitting adds no charge. Empty power destroys a drone even with armor. Cubes fit three separated drones and do not add solid collision geometry. No hardcoded roles, income without a living drone in a resource cube, or starting resource pile. Payload drops and replacement airframes remain deferred per [STRATEGY-PLAN.md](STRATEGY-PLAN.md).
- Jammer interference closes/reopens native Zenoh sessions through one serialized reconciler. It affects nearby allies and the emitter, preserves durable queued mail and combines with manual isolation and destruction. Clearing interference cannot reconnect a manually isolated or destroyed drone. Cameras, local controller and private reasoning continue. Only own charge/capacity and jammer/interference status are allowed equipment feedback; no jammer source, range, affected roster or world geometry enters actor tools.
- Preserve finite shared income, atomic purchases, one-hit armor, lethal unarmored building/terrain/drone contacts, armor deflection, friendly fire and last-team-standing victory. Destroyed drones must stop mining/moving, lose tools and retire their actors. `shared/fleet.ts` distinguishes the three-member default roster from the six-member match roster; use `MATCH_FLEET`/`MATCH_DRONE_IDS` for the entire match.
- Every drone starts each fresh match with one free armor charge and empty module slots; each team still has 30 shared salvage for its first purchase. An absorbed collision stops the current movement and sends local collision/armor-loss feedback. Bullet absorption sends generic hit/armor-loss feedback. Keep these alerts free of attacker/obstacle identity, impact coordinates and hidden telemetry. A second unprotected hit is lethal; replacement armor is a normal paid purchase, and empty batteries remain fatal despite armor.
- Preserve OpenStreetMap attribution and documented approximations when editing the city. Source evidence is in [CINCINNATI-SOURCES.md](CINCINNATI-SOURCES.md); regenerate `shared/city-data.json` with `node scripts/build-city.mjs` after source-data changes.

## Local data
