# Fleet PoC integration contract

Build a real local Three.js game with a Codex parent and three native child drones. All gameplay inference MUST use `gpt-5.6-luna` / `xhigh`, including the relay parent. Never silently substitute another model or separate independent sessions for native children.

Workspace: this directory. Node 24, TypeScript, Vite, Three.js, Express, ws, MCP SDK. Main coordinator owns package setup, shared/types.ts, server/game.ts, server/index.ts, tests/game.test.ts and README. UI maker owns client/* and index.html. Runtime maker owns server/runtime*.ts and runtime supporting files/tests only. Communicate contract changes before making them.

## Browser wire contract

Same-origin WebSocket `/ws`. Server -> browser `{type:'state',state}` ~20 Hz; `{type:'capture',requestId,droneId,pose,simTime,drones}`. Browser -> server `{type:'capture-result',requestId,image}` where image is a JPEG data URL rendered at the supplied own pose and peer poses from the same instant. The browser receives world state for rendering; the agents receive only image pixels and their allowed sensors. HTTP POST `/api/start` starts live Luna/xhigh runtime; POST `/api/stop` stops it; POST `/api/mission` body `{text}` queues player instruction; POST `/api/speed` body `{speed}` updates speed; POST `/api/reset` resets stopped world. GET `/api/state` returns state. JSON errors `{error}`.

State: `{simTime,mission,running,speed,completed,pads,obstacles,drones,radio,runtime}`. `pads`: `{id,color,x,z}` array with color CSS string; `obstacles`: `{x,z,width,depth,height}` array. Drone `{id,x,y,z,yaw,pitch,status,action?,online,observations}`. y up; yaw 0 faces -Z, positive yaw rotates left toward -X; pitch degrees positive up. Action optional `{id,kind,target?:{x,y,z}}`. radio `{id,from,to,kind,text,simTime,mission}`. Runtime `{status,message,model,effort,threadId?,children?,usage?}`. Coordinates world +/-30, altitude 1..18. Browser may show world; only camera snapshots + own pose go to agents.

## Runtime interface

`server/runtime.ts` exports `CodexFleetRuntime` constructor `{projectDir:string,toolHandler: async(role, name,args)=>MCP CallToolResult,onStatus:(partialRuntimeState)=>void,onEvent:(event)=>void}`; methods `async start()`, `async stop()`. Roles `parent | drone-1 | drone-2 | drone-3`. Runtime owns connection-scoped role identity, MCP wiring, native subagent bootstrap, model verification, lifecycle. Must not start any inference using a model other than Luna/xhigh. No arbitrary model-chosen drone ID. Please report impossible constraints honestly.

Parent tool `forward_next_instruction({})` holds async wait and forwards queued original player text. Drone tools: `observe({})`, `act({mission:number,kind:'fly_to'|'look'|'hover',x?,y?,z?,heading?,pitch?})`, `send({mission:number,to:'all'|'drone-1'|'drone-2'|'drone-3',kind:'chat'|'found'|'claim'|'done',text:string,data?:object})`, `wait({after?:number,timeout_ms?:number})`. Schemas live in runtime-tools.ts; game.ts owns behavior. Every running drone result is a `fleet-observation/1` bundle with tool outcome, all unread events, cursor, session/mission, current action ID/kind, and `sensors:{position,heading,timestamp,camera}` plus an actual image content block. Sensor capture failure is explicit. Wait wakes without consuming mail; the response wrapper drains mail after capture. Parent results never include these bundles. Stop rejects/resolves waits.

Agent boundaries: no world-axis mapping, scale, speed, bounds, ground plane, camera calibration, target appearance/positions, scoring thresholds or global completion events. Heading is exposed; tilt is not. Receipts may echo commands but do not disclose controller geometry. World details above are developer-only. Unread mail is retained; queues are memory-only. Radio uses `fleet-radio/1` with session UUID, unique ID, sequence and UTC send time in addition to the fields above. True network transport is future work described in COMMUNICATION-PLAN.md.

Use fixed equal child instructions for tools/cooperation and clean initial contexts, no mission planning by parent. No prior target coordinates in agent context. Gameplay target: find three colored pads and hover one drone above each. Parent only launches children then calls relay tool. Enforce tool isolation using actual runtime features where supported; document any prompt-only boundary. Manual/demo behavior must be clearly labelled and cannot count as live playtest.
