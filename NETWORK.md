# Protocols in the game

The game uses native Zenoh and MAVLink 2 on loopback. It does not install an operating-system radio mesh. Network lab buttons simulate an entire drone's partition by closing/reopening its native Zenoh session. Jammer-driven partitions remain available only in historical rules; cargo-v1/v2 have no active jammer purchase or tool. Physical RF propagation, ordinary link range, arbitrary per-edge loss, multihop radio routing and bandwidth constraints remain unmodeled.

```text
Player blue chat/objective         Fixed initial red objective
           |                                  |
  blue mechanical parent             red mechanical parent
           |                                  |
 blue operator Zenoh bridge          red operator Zenoh bridge
           |                                  |
 blue drone-1 / drone-2 / drone-3     red drone-4 / drone-5 / drone-6
       native peer graph                 native peer graph
           |                                  |
           +------ six MAVLink 2 UDP pairs ---+
                              |
                     Node RTS simulation
```

Each team has a complete four-peer graph: three drone bridges and one operator. There is no radio edge between teams. The blue operator receives group messages and direct messages addressed to `player`, and can send ordinary group/direct chat. The red operator remains an objective publisher; ordinary player access to red is rejected by both application and native worker checks. Neither operator routes peer messages or plans for its team. Native hosting, physics and browser rendering share one application. Six clean-context Luna/xhigh drone actors belong to two mechanical parent sessions. Both teams receive the same opening objective. Later ordinary player chat does not replace that objective or cancel work.

## Setup and scope

Run `npm ci`, `npm run network:setup`, then `npm run dev`. Setup creates a project `.venv` and installs pinned `eclipse-zenoh==1.10.1` and `pymavlink==2.4.49`. Tested interpreter: Python 3.12.4. Set `FLEET_PYTHON` to an existing interpreter with these dependencies if using a different environment. Default gameplay requires the protocols; there is no automatic in-memory fallback.

Every bridge opens an OS-assigned loopback TCP port, uses Zenoh `peer` mode, explicit peer endpoints, and no multicast/gossip discovery or central router. Native sessions exchange data even while no model tool is running. See [Zenoh deployment documentation](https://zenoh.io/docs/getting-started/deployment/) and its [Python implementation](https://github.com/eclipse-zenoh/zenoh-python).

Each drone's control/telemetry pair exchanges actual binary MAVLink 2 UDP datagrams. Decoded setpoints determine movement; decoded own pose, velocity and camera orientation feed local sensing. The browser acquires the separate camera sample. The vehicle interface now documents its coordinate frame, calibration and limits; battlefield geometry stays private. This is a small simulated endpoint profile, not PX4/ArduPilot SITL. Exact messages and limits are in [MAVLINK.md](MAVLINK.md). Zenoh, pymavlink, host Python/OS and the vehicle bridges are fixed platform infrastructure, outside the guest library partition; this does not claim their whole installation fits the 8 MiB application package.

## Delivery rules

`shared/fleet.ts` owns the explicit blue/red and combined match rosters. `server/team-session.ts` creates two `FleetNetwork` instances with separate random `networkId` UUIDs under the same match session. Worker membership, broadcast recipients and acknowledgement expectations derive from each team's roster; Python validates it at startup. Namespaced topics, endpoints and SQLite stores remain separate. MCP tool destinations and game receive checks also reject opposing-team roles. `DEFAULT_FLEET` is still the three-member blue roster for reusable single-network adapters; `MATCH_FLEET` is the complete six-drone match.

Radio publications use `fleet/<networkId>/radio/group` and `fleet/<networkId>/radio/direct/<recipient>`, with separate ACK keys. A blue drone broadcast targets its two teammates and player; a red drone broadcast targets its two teammates. Operator broadcasts target all three drones. Sender identity is bound by the worker role, with match/network UUID, boot identity and monotonically increasing per-boot sender sequence attached by the native bridge. Retried message bindings are retained in the charged outbox/tombstone, including across worker restarts. Namespaced topics are isolation, not cryptographic authentication. Each drone adopts an explicitly versioned `mission` only on actual native delivery. Radio-isolated drones retain their last objective. Ordinary chat/status and inert file receipts never replace objectives.

The versioned `fleet-radio/1` JSON message is carried in a native envelope. Outgoing payloads, per-recipient receipts, incoming payloads and deduplication records all consume the peer's radio allocation. Incoming storage commits before ACK. A full receiver emits backpressure without an ACK; the sender retains its bounded outbox and retries. One disconnected recipient does not block delivery to others. Retries preserve message identity and original content. Per-recipient `stored` events mean durable storage; the legacy aggregate `received` event means every expected recipient stored the message. Neither proves model inclusion, understanding, agreement or action completion. The model bundle records inclusion separately, and explicit replies/action reports remain agent-authored.

Retries use monotonic host time with exponential backoff from 250 ms to 4 s. Ordinary mail defaults to 120 s and cannot exceed 600 s. `status` is an explicitly agent-selected latest-value class with at most 5 s lifetime; newer status supersedes the previous same-sender value and stale status does not replay after reconnection. Each scheduling pass submits at most 16 due messages, ordering objective traffic first and transfer chunks after ordinary traffic. Ordinary text is capped at 1,200 characters and the complete UTF-8 envelope at 8 KiB. Host-bound objectives allow 6,000 characters within that same envelope cap, accommodating the full opening briefing; player-entered replacement objectives remain limited to 4,000 characters. A rejected objective relay reports a terminal match failure instead of leaving actors indefinitely awaiting a missing objective. Transfer messages are capped at 10 KiB including metadata. The native callback queue is bounded to 128 frames and rejects oversize frames before application admission. Queue overflow has no receipt and relies on durable sender retries.

Transport retry/expiry clocks are independent of simulation speed and pauses. UTC expiry labels are presentation metadata. Native helper restarts on the same host preserve monotonic deadlines and durable unread mail; a fresh match uses a new identity and does not replay earlier knowledge. Cross-host migration and operating-system reboot recovery are outside this match-scoped profile. A helper failure explicitly stops the live match; there is no silent transport replacement or automatic recovery of a model's private context.

## Storage and private file exchange

Each drone has a 4 MiB durable-mail partition. The implementation conservatively limits SQLite itself to 3.75 MiB, leaving 256 KiB for its rollback transaction peak. It also reserves that 256 KiB from the shared 1 MiB staging partition; this double reservation deliberately reduces usable capacity instead of borrowing space. SQLite file pages, indexes, row metadata, receipt state and tombstones count, including freelist pages still present on disk. `DELETE` journals, full synchronous commits, fixed page limits, cache-spill prevention and bounded row transactions avoid unbounded WAL/checkpoint growth. Storage status reports actual backing-file bytes, journal peak, reusable pages, quota and queue pressure.

Ordinary traffic cannot use the final 64 KiB or 16 admission slots reserved for host-bound objectives. Unread mail plus pending sends normally has a 256-record limit; deduplication records have a separate bounded ceiling of 2,048. Consumed incoming and fully stored outgoing payloads are cleared while SHA-256 identity tombstones remain until original retry expiry. Expired outgoing mail and expired consumed tombstones are collected incrementally. Durable unread payloads remain until explicit consumption, even after expiry; the model boundary reports expiry rather than silently deleting unseen mail. Latest status is the intentional ephemeral exception. Small incremental vacuum operations reclaim pages without an unbounded temporary database. Capacity exhaustion returns an actionable partition/queue error rather than deleting authored or unread content.

`transfer` offers one existing private UTF-8 `.md`, `.txt`, `.json`, `.js` or `.mjs` file to one teammate. Files remain limited to 64 KiB. Every low-priority chunk carries the announced transfer ID, filename, total bytes, SHA-256 and bounded deadline, so out-of-order delivery needs no uncharged pending-announcement queue. Chunks contain at most 4 KiB of UTF-8 data and preserve Unicode boundaries. Received source travels through actual native mail before entering inert, quota-reserved recipient staging. The recipient verifies all ordered chunks and the content hash, then sends a separate native completion result. A storage receipt is not this completion result.

The actor chooses `list`, `status`, `import` or `cancel`. Import requires the recipient's chosen workspace destination path and the normal atomic workspace allocation; receiving a filename never authorizes overwriting an existing file. Verified source never starts a routine automatically. No archives, decompression, package installation, synchronized team folder or arbitrary imports are supplied. Sender copies, receiver staging, metadata, verification/encoding peaks and pending RPC copies are charged to their own staging allocations. Source reservations remain held until outstanding submissions settle even after cancellation. At most 32 active/retiring transfers and 32 pending transfer submissions per drone are admitted. Cancelled/imported transfers retain a charged 1 KiB identity tombstone until the original deadline so a reordered chunk cannot recreate their staging. Expiry releases that metadata; cancellation releases payload/verification allocations after retained work settles. Partitions can delay the peer's cancellation notice until delivery or expiry. A completely full staging partition can also prevent a negative completion reply, so sender status must not interpret a missing completion as success.

The remaining staging capacity is shared with atomic workspace operations, not a separate allowance for each transfer. Workspaces and inert transfer copies are bounded virtual storage belonging to one drone for one match. Native SQLite stores live in `artifacts/network/<session>/<networkId>/`; host replay/audit copies remain inaccessible to agents. See the onboard workspace/runtime documentation for the remaining application partitions and measured guest package manifest.

Stop terminates both native sessions and all protocol workers. Match completion also shuts them down. Destroying a drone retires its model actor, revokes tool access and disconnects its radio peer. Merely isolating a live peer leaves its sensors and controller available and its last received mission active. The player's global Stop is an application lifecycle operation, not evidence of an emergency radio command crossing a partition. Mining, attachments and firing are local simulator operations; peer coordination still travels through native radio.

Jammers apply the same native partition mechanism automatically to nearby drones, including the emitter and its allies. `TeamSession` serializes link transitions and combines the current interference flag with manual isolation, actor retirement and destruction. A newer desired state is reconciled after an in-flight native transition completes; clearing interference never overrides another reason for isolation. A radio send waits for pending reconciliation before queueing through the native sender. Packets already in flight before a transition may have arrived; the system does not erase delivered mail or claim instantaneous physical RF behavior. Link failures use the existing explicit session-failure path. Simulation ticks and camera capture do not wait on radio reconnection.

## Reuse on hardware

The JSON coordination semantics and native Zenoh bindings can be reused, but this launcher intentionally accepts loopback endpoints only. A deployment adapter would supply actual peer addresses over a tested IP mesh, peer authentication, clock synchronization, bounded durable storage and reconnection policy. An IP mesh such as Linux batman-adv supplies network forwarding beneath Zenoh; Zenoh does not configure the radios. [Linux mesh documentation](https://docs.kernel.org/networking/batman-adv.html)

The simulated MAVLink endpoints would be replaced with actual vehicle endpoints, with autopilot-specific mode negotiation, heartbeat/setpoint streaming, controller limits, timestamp alignment and loss handling. A local controller must run independently of LLM latency. PX4 documents its continuous offboard proof-of-life requirement. [PX4 Offboard](https://docs.px4.io/main/en/flight_modes/offboard)

The simulation is a protocol integration step, not evidence of hardware flight readiness. The new own-vehicle interface includes local velocity, finite range sensors, frame/units and camera calibration. It still provides no hidden map, resource coordinates, target identity or scoring oracle.

## Evidence

`tests/network-peer.test.ts` and `tests/network-roster.test.ts` exercise real-process Zenoh delivery, partition, backoff, expiry, duplicate/restart behavior, latest status, namespace isolation and blue ordinary chat/replies. `tests/radio-store.test.ts` exercises actual SQLite/journal bytes under sustained writes, quota reserve, unread retention, tombstones and atomic SQLite-full rollback. `tests/radio-transfer.test.ts` includes real native partitioned Unicode source transfer plus inert import, malformed hashes, source quota and slow-submission cancellation regressions. Integrated game/runtime tests cover actual per-drone objective adoption; transport tests alone do not prove model comprehension or teamwork. These fixtures use no inference. Historical reports apply only to their recorded revisions.

The historical single-team Luna/xhigh browser trial confirmed partition/reconnection, queued mission delivery and replies from all three drones, but did not complete its three-movement criterion. [NETWORK-PLAYTEST.md](NETWORK-PLAYTEST.md) records those limits. Current RTS browser QA uses `scripts/verify-rts.ts` without inference and `scripts/playtest-rts.ts` for bounded real two-team trials, both on isolated port 4318 after checking `/api/state`. See [RTS-PLAYTEST.md](RTS-PLAYTEST.md) for current evidence. Preserve active player sessions on port 4317.

Admin now exposes bounded, searchable session audits, including new Zenoh application payload records with topics, envelopes, acknowledgements, direction and byte counts. Logging samples at most 12 payloads per peer per second, recording suppression counts; it is not a TCP framing capture. MAVLink records contain actual CRC-validated datagram hex and decoded fields, with telemetry limited to one sample per message type per second and an overall 20 packets/drone/s logging cap. Transport behavior remains unsampled; these caps affect diagnostics only. Older sessions retain their original publication/receipt and operation records.
