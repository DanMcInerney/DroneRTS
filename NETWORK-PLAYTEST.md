# Network live playtest

This is the single bounded live trial run on 13 September 2026 against `http://127.0.0.1:4318` using isolated Playwright Chromium with SwiftShader. The parent and all three native children reported `gpt-5.6-luna / xhigh`; startup reached three online drones, four ready Zenoh workers (three drones plus operator), `zenoh-tcp`, and `mavlink2-udp`. The run lasted 29.3 seconds after Mission 1 forwarding and stopped 4318 in cleanup. Port 4317 was not used.

The Network lab rendered active, isolated, and recovered desktop states. Clicking Isolate on drone 3 produced `drone3Online: false`; after the second instruction, the UI showed `pendingMissions: 1` and no Mission 2 radio sender from drone 3 at the seven-second checkpoint. Clicking Reconnect returned drone 3 online, drained pending missions to zero, and the UI radio showed Mission 2 replies from all three drones. Each Mission 2 reply acknowledged the instruction and contained a position and timestamp report. The 390px checks before and after recovery both had no horizontal overflow, a visible Network lab, and all peer cards fitting the viewport.

The run fails the full Mission 1 movement criterion and the requested zero-error criterion. The harness advanced to isolation after seeing three Mission 1 radio claims and sensor bundles, before all three movement actions completed. The checkpoint itself sampled zero displacement for all drones. Later audit/state evidence shows drone 3 completed one `fly_to` from `(5,7,23)` to `(5,8,23)` (`dy: +1`); drone 1 and drone 2 then attempted Mission 1 `fly_to` calls after Mission 2 had arrived and received stale-mission errors, so they did not move. The audit contains three `tool-error` records for these stale commands. This is a real timing failure in the bounded trial, so the report does not claim three completed movements.

The audit did verify Mission 1 Zenoh receipts for all three drones, Mission 2 delivery after recovery, and the four sensor fields (`position`, `heading`, `timestamp`, `camera`) on Mission 1 observations for every drone. The audit has 16 camera metadata records and zero `data:image` payloads; the previous redaction boolean was not evidence of leakage and is replaced by this direct check. MAVLink audit evidence contains one successful binary wire operation for drone 3 (`SET_POSITION_TARGET_LOCAL_NED`) and no MAVLink fatal/error events; it does not establish three successful Mission 1 wire actions because the other two commands were rejected before wire acceptance. Browser console/page errors were empty. The audit records drone 3's Mission 2 receipt after the isolated seven-second UI checkpoint; its exact ordering relative to the reconnect request is not claimed because the original run recorded the reconnect timestamp after the API call completed. The observed network is explicit loopback Zenoh peer transport; this trial makes no RF mesh or multi-hop claim.

The test harness is [scripts/playtest-network.ts](scripts/playtest-network.ts). It now waits for a measurable movement and completed hover state for each drone before starting the partition phase, timestamps the reconnect request before clicking, and marks audit errors as failures. The parent completed the harness typing fixes and the final TypeScript/Vite build passed. These harness changes were not rerun with inference; the recorded run remains the single trial described above.

The trial server used the normal network implementation before the independent review's telemetry-failure repair. That failure path was verified separately by a regression in the final 41-test suite. The idle test server was closed after cleanup; the user-facing server on port 4317 was restarted with the final implementation and left idle.
